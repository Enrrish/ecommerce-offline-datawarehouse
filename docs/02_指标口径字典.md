# 指标口径字典

数仓里所有"口径"都写进 SQL 的 `COMMENT` 里，这份文档是它们的汇总说明。
**口径的优先级高于 SQL——口径错了，SQL 写得再漂亮也是错的。**

---

## 0. 通用约定

| 约定 | 说明 |
|---|---|
| 金额字段 | 统一命名 `gmv` / `total_gmv` / `monetary`，类型 `DECIMAL(14,2)`。**源数据无 `quantity`，严格含义是"成交单价之和"** |
| 比率字段 | `DECIMAL(10,4)`；占比字段 `DECIMAL(10,6)` |
| 除零处理 | 分母为 0 时结果一律为 `NULL`，不用 0 填充（0 会被误读成"转化率为零"） |
| 缺失维度 | `category_code` / `brand` 缺失保留为 `未知品类` / `未知品牌` 单独成组，**不丢弃**，保证各表金额加总等于大盘 |
| 业务日期 | 分区字段统一命名 `dt`，格式 `yyyy-MM-dd`，取自 `event_time` 的日期部分 |

---

## 1. ODS 层

零加工贴源，不做任何类型转换与过滤。

| 项 | 口径 |
|---|---|
| 字段类型 | **全部 STRING**。原因是源 CSV 存在空串、脏值，一旦在 ODS 定成数值类型，异常值会变成 NULL 且不可逆，排查时无法还原 |
| 表类型 | 外部表（EXTERNAL），`DROP TABLE` 不会删除 HDFS 原始数据 |
| 存储 | TEXTFILE + OpenCSVSerde（贴源保持可读） |
| 分区 | `dt`，每日一个目录，上传幂等（先删分区目录再 put） |
| 拆分基准 | `split_source.sh` 产出的 `_manifest.txt` 记录每日行数，供 ODS 上传后回验 |

---

## 2. DWD 层

| 项 | 口径 |
|---|---|
| **行守恒** | 不做任何 `WHERE` 过滤，DWD 行数必须严格等于 ODS 行数（9,244,421）。脏数据留在明细层，由下游按需处理 |
| 类型收敛 | `event_time`→TIMESTAMP，`product_id`/`category_id`→BIGINT，`price`→DECIMAL(10,2) |
| 空值处理 | 空串与纯空格一律 `NULLIF(TRIM(x), '')` 转 NULL |
| 去重 | `ROW_NUMBER() OVER (PARTITION BY event_time, user_id, product_id, event_type, user_session ORDER BY ...)`，取 `rn=1`。tie-breaker：有 brand / price 的记录优先，避免随机丢弃有信息量的那条 |
| 派生字段 | `event_hour`（取 `event_time` 的小时） |
| 存储 | ORC + Snappy，459.8 MB（CSV 源 1.1 GB，省约 58%） |

**数据质量实测**：`price = 0` 的 12,850 条全部是 `view` 事件，不存在 0 元订单；`brand` 为 NULL 的有 1,216,756 条（13%）。

## 3. DWS 层

DWS 是**引入业务口径的第一层**，聚合逻辑一旦定错，ADS 全错。

### 3.1 用户日表 `dws_user_action_day`

| 字段 | 口径 |
|---|---|
| `view_cnt` / `cart_cnt` / `purchase_cnt` | 当日该事件的**次数**（PV，同人多次累加） |
| `total_gmv` | `SUM(price)`，仅统计 `purchase` 事件 |
| `first_active_date` | 来自维表 `dim_user_first_active`，取全期 `MIN(dt)` |
| `is_new_user` | 1 = 当日为首次活跃。**注意数据集首日的偏差，见踩坑记录第 10 条** |

### 3.2 商品日表 `dws_product_action_day`

| 字段 | 口径 |
|---|---|
| `category_code` / `brand` | 取**当天事件中的值**（日快照），用 `MAX()` 忽略 NULL |
| 为什么不做全期回填 | 同一商品 30 天内可能换过品牌，日快照能保留变更痕迹；全期最新值会让历史报表"回溯变形"（今天改了品牌，昨天的报表也跟着变） |

### 3.3 同日漏斗 `dws_user_funnel_day`

| 字段 | 口径 |
|---|---|
| `view_users` / `cart_users` / `pay_users` | 当日有过该行为的**人数**（去重），不是次数 |
| `strict_funnel_users` | 当日**走完 浏览→加购→支付 三步**的人数 |
| `view_to_cart_rate` | 加购人数 / 浏览人数 |
| `cart_to_pay_rate` | 支付人数 / 加购人数。**会 > 1，实测 1.67~4.02** |
| `view_to_pay_rate` | 支付人数 / 浏览人数，**主转化指标**（实测 3.5%~5.1%） |

> **为什么 `cart_to_pay_rate` 会大于 1**：源数据 `cart` 事件仅占 1.06%，`purchase` 占 3.15%，
> 大量用户浏览后直接下单、不经过加购。所以"加购→支付"不是主转化路径，这个比率仅作参考；
> 真正反映加购环节损耗的是 `strict_funnel_users`。

## 4. ADS 层

### 4.1 大盘日报 `ads_trade_overview_day`

| 字段 | 口径 |
|---|---|
| `active_users` | 当日有过任意行为的用户**去重**数 |
| `new_users` / `old_users` | 新客数 / 活跃 − 新客 |
| `view_pv` / `cart_pv` / `purchase_pv` | 当日事件次数（PV，不去重） |
| `pay_users` | 当日有 `purchase` 行为的用户去重数 |
| `avg_order_value` | GMV / 订单数（客单价） |
| `arpu` | GMV / 活跃用户数（人均成交金额） |

### 4.2 漏斗分析 `ads_user_funnel_day`

在 DWS 漏斗基础上补充**新老人群拆分**：`new_pay_users` / `old_pay_users` / `new_user_gmv` / `old_user_gmv` / `new_gmv_ratio`。
校验：新客下单 + 老客下单 = 当日支付人数（规则 5）。

### 4.3 留存 `ads_user_retention_day`

| 项 | 口径 |
|---|---|
| 粒度 | `dt` = **新增日期（cohort）**，一个 cohort 一行 |
| 第 N 日留存人数 | `DATEDIFF(活跃日, 首活日) = N` 的活跃人数。**精确匹配，不是"N 天内活跃过"的模糊口径** |
| 留存率 | 第 N 日留存人数 / 该 cohort 新增人数 |
| **观察窗口不足** | 首活日 + N 天 > 数据最大日期时，结果置 **NULL**，不拿部分数据凑数。实测：次日可算 30 个 cohort、15 日 16 个、30 日仅 1 个 |
| `is_data_start_cohort` | 1 = 数据集首日的 cohort，其"新用户"实为存量用户，留存率不可信 |

### 4.4 商品 TOP 榜 `ads_product_rank_day`

| 项 | 口径 |
|---|---|
| 取数 | 当日 GMV 前 50 名 |
| 排序 | `total_gmv DESC, product_id ASC`，**加 product_id 兜底保证结果可复现**（并列时不会因执行顺序变化而换榜） |
| `gmv_share` | 该商品 GMV / 当日大盘 GMV，用窗口 `SUM(total_gmv) OVER (PARTITION BY dt)` 取分母，避免自关联 |
| `view_to_pay_rate` | 购买次数 / 浏览次数，浏览为 0 时为 NULL |

### 4.5 品类分析 `ads_category_sales_day`

| 项 | 口径 |
|---|---|
| 粒度 | `dt` × `category_code`，每天约 124 行，**全品类不截断** |
| `cat_level1` | 取品类码第一段（`SPLIT(category_code, '\\.')[0]`）。源品类码是层级结构（如 `appliances.kitchen.washer`），带上一级名可直接支持下钻，不必再建一张表 |
| `sku_cnt` | 当日产生过行为的商品数 |
| `gmv_rank` | 当日品类 GMV 排名 |

### 4.6 品牌榜 `ads_brand_sales_day`

当日 GMV 前 30 名，其余同品类表。

### 4.7 RFM 用户价值 `ads_user_value_rfm`

| 项 | 口径 |
|---|---|
| 粒度 | `user_id`，全期快照；分区 `dt` = 统计截止日 |
| R（recency_days） | 最近购买日距统计截止日的天数 |
| F（frequency） | 全期累计购买次数 |
| M（monetary） | 全期累计成交金额 |
| **R 打分（固定区间）** | ≤3 天=5，≤7 天=4，≤15 天=3，≤25 天=2，其余=1。固定阈值保证**跨月可比** |
| **F 打分（固定区间）** | 1 次=1，2 次=2，3 次=3，4-5 次=4，≥6 次=5。**不用 NTILE**：离散小整数并列值极多，NTILE 会把同样行为的用户随机切进不同桶 |
| **M 打分（NTILE 等频）** | `NTILE(5) OVER (ORDER BY monetary ASC)`，金额是连续长尾变量，等频最合理。**只对有购买行为的用户分桶**——否则 281 万未购买用户会占满第 1 桶，让购买用户的分数全部失真 |
| **未购买用户** | 不参与打分，单独归入「未购买用户」层。RFM 模型本身只描述交易客户 |
| 8 类分层 | 以 3 分为界，按 R/F/M 高低组合：重要价值 / 重要保持 / 重要发展 / 重要挽留 / 一般价值 / 一般保持 / 一般发展 / 一般挽留 |

**实测分层结果**（GMV 加总 = 74,948,758.44，与大盘完全一致）：

| 分层 | 人数 | GMV |
|---|---|---|
| 未购买用户 | 2,813,283 | 0.00 |
| 重要发展客户 | 61,534 | 27,993,099.45 |
| 重要挽留客户 | 49,392 | 21,762,283.92 |
| 一般发展客户 | 42,714 | 2,871,559.19 |
| 一般挽留客户 | 39,737 | 2,685,406.78 |
| 重要价值客户 | 11,025 | 15,963,063.77 |
| 重要保持客户 | 3,251 | 3,586,184.46 |
| 一般价值客户 | 716 | 61,456.39 |
| 一般保持客户 | 301 | 25,704.48 |

## 5. 边界情况处理清单

| 情况 | 处理 |
|---|---|
| 分母为 0 | 结果为 NULL |
| `category_code` / `brand` 为 NULL | 保留为「未知品类」/「未知品牌」分组，金额计入大盘 |
| 用户从未购买 | RFM 中 R/F/M 分为 NULL，归入「未购买用户」层 |
| 留存观察窗口不足 | 结果为 NULL |
| 数据集首日 cohort | `is_data_start_cohort = 1`，留存率不可信 |
| 榜单并列（GMV 相同） | 用 `product_id` / `brand` 升序兜底，保证可复现 |
