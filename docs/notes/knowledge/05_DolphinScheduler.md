# DolphinScheduler 知识卡

> 项目用它把 `ODS → DWD → DWS → ADS` 串成一条 T+1 工作流，解决"谁先跑、失败怎么办、历史怎么补"。

---

## 1. 为什么不用 crontab

| 能力 | crontab | DolphinScheduler |
|---|---|---|
| 定时 | 有 | 有（cron/可视化） |
| 任务依赖 | 自己写锁/等文件 | DAG 依赖，上游成功才跑下游 |
| 失败重试 | 自己写 | 内置重试/失败策略 |
| 补数 | 自己循环 | 选日期范围自动生成实例 |
| 可视化 | 无 | 有（DAG、状态、日志） |
| 告警 | 自己接 | 内置告警 |
| 并发控制 | 自己写 | 串行/并行策略 |
| 多租户 | 无 | 有 |

一句话：**crontab 只会"到点执行"，调度系统负责"按依赖执行、失败可控、历史可补"。**

## 2. 架构：四个服务 + 两个外部依赖

```
            ┌────────────┐
  浏览器 ──▶│  api-server │  提供 REST API 和 UI
            └─────┬──────┘
                  │ 读写元数据
            ┌─────▼──────┐
            │   MySQL    │  工作流定义、实例、任务状态
            └─────▲──────┘
                  │
            ┌─────┴──────┐        ┌──────────────┐
            │ master     │◀──────▶│ ZooKeeper    │  注册/选主/协调
            │ (调度)      │        └──────▲───────┘
            └─────┬──────┘               │
                  │ 分发任务               │
            ┌─────▼──────┐        ┌──────┴───────┐
            │ worker     │        │ worker       │  真正执行脚本
            └─────┬──────┘        └──────┬───────┘
                  │                      │
                  └────────┬─────────────┘
                     ┌─────▼──────┐
                     │ alert-server│ 告警
                     └────────────┘
```

| 服务 | 职责 | 挂了会怎样 |
|---|---|---|
| api-server | UI/接口、元数据读写 | 页面打不开，但已提交的任务还在跑 |
| master-server | 生成工作流实例、拆分任务、分发、状态机 | 无法调度新实例；多 master 会选主 |
| worker-server | 真正执行 Shell/SQL 任务 | 该 worker 上的任务失败/重新分配 |
| alert-server | 发告警 | 不影响执行，只是收不到通知 |

**关键理解**：master 不执行脚本，只"派活"；worker 才是执行者。所以 worker 节点必须装好 Hive/Hadoop 客户端、能访问数据。

## 3. 核心概念对照

| 概念 | 类比 | 说明 |
|---|---|---|
| 项目 Project | 文件夹 | 工作流的逻辑分组 |
| 工作流定义 Process Definition | 剧本 | DAG + 全局参数，可多版本 |
| 工作流实例 Process Instance | 一次演出 | 每次运行/补数生成一个 |
| 任务定义 Task Definition | 角色 | 一个节点干什么 |
| 任务实例 Task Instance | 一次出场 | 某次运行里的某个节点 |
| 租户 Tenant | 执行身份 | 必须是目标机器上真实存在的 Linux 用户 |
| Worker 分组 | 执行队列 | 任务可以指定去哪组 worker 跑 |
| 环境 Environment | 启动配置 | 指定 JDK/PATH 等 |
| 全局参数 | 剧本级变量 | 所有节点可见 |
| 本地参数 | 角色级变量 | 当前节点可见 |

> 排障时先分清：**定义错了**（改工作流）还是**实例错了**（看这次运行）；**任务定义错了**还是**任务实例错了**。

## 4. 一次调度发生了什么

```
定时到点 / 手动运行
   ↓
master 生成工作流实例（process instance）
   ↓
按 DAG 找到入度为 0 的任务，生成任务实例（task instance）
   ↓
任务进入命令队列（t_ds_command）
   ↓
master 根据 worker 注册信息分发任务
   ↓
worker 接收任务 → 生成临时 shell 脚本 → 执行
   ↓
退出码 0 → SUCCESS；非 0 → FAILURE
   ↓
master 收到状态，推进下游任务
   ↓
全部成功 → 工作流 SUCCESS；任一失败 + 失败策略=结束 → 工作流 FAILURE
```

**退出码是调度系统和脚本之间唯一的契约**。脚本最后 `exit 0/1` 写错，UI 上的红绿就是错的。

## 5. 参数体系

### 三类参数

| 类型 | 作用域 | 例子 |
|---|---|---|
| 全局参数 | 整个工作流 | `bizdate` |
| 本地参数 | 单个任务 | `table_name` |
| 内置参数 | 系统提供 | `${system.biz.date}`、`${system.biz.curdate}` |

### 时间格式的坑

| 写法 | 输出 | 适用 |
|---|---|---|
| `${system.biz.date}` | `yyyyMMdd` | 分区是 `20240101` 格式 |
| `$[yyyy-MM-dd-1]` | 昨天，带分隔符 | 分区是 `2024-01-01` 格式 |
| `$[yyyy-MM-dd]` | 今天 | 看场景 |

本项目分区是 `dt=2019-10-01`，所以必须用 `$[yyyy-MM-dd-1]`，**不能用内置 `${system.biz.date}`**。

### 参数怎么传到脚本

Shell 节点里：

```bash
echo "[ODS] bizdate=${bizdate}"
bash /home/cy/scripts/ods/ods_load.sh ${bizdate}
```

`${bizdate}` 是 DS 在生成临时脚本时替换掉的，不是 shell 环境变量。

## 6. 补数：最容易错的地方

### 两个日期

| 概念 | 含义 |
|---|---|
| 调度日（补数填的日期） | "假装今天是哪天" |
| 业务日（bizdate） | 实际要处理的数据日期 |

如果全局参数是 `bizdate = $[yyyy-MM-dd-1]`，那么：

```
补数填 D  →  bizdate = D - 1
```

想跑业务日 `2019-10-01`，补数要填 **`2019-10-02`**。

### 直接"运行" vs "补数"

- **运行**：按当前时间算 `bizdate`（通常是昨天）；
- **补数**：按你选的调度日算 `bizdate`。

所以拿历史数据测试时，直接点"运行"会因为"昨天没有源文件"而失败——这不是 bug，是脚本的前置校验在保护你。

### 补数的代价

补 N 天 = 生成 N 个工作流实例，**串行/并行取决于执行策略**。如果每天都要全期重算（如留存/RFM），补一个月可能非常慢，历史回填优先用脚本的批量模式。

## 7. 两种"策略"，别搞混

### 执行策略（同一个工作流多次触发）

| 策略 | 行为 |
|---|---|
| 串行等待 | 排队，前一个跑完再跑下一个 |
| 串行抛弃 | 前一个没跑完，新实例直接丢弃 |
| 串行优先 | 新实例优先，旧的让路 |
| 并行 | 同时跑 |

### 失败策略（任务失败后怎么办）

| 位置 | 推荐 | 理由 |
|---|---|---|
| 工作流内部 | **结束** | 上游 ODS 失败就不该跑 DWD，防止脏数据扩散 |
| 定时调度自身 | **继续** | 今天失败不能让明天永久停摆 |

一句话：**用"结束"保数据正确，用"继续"保调度不断。**

## 8. 资源与负载保护

worker 会在任务执行前检查自身负载：

```yaml
worker.server-load-protection:
  enabled: true
  max-system-memory-usage: 0.9
  max-cpu-usage: 0.9
  max-disk-usage: 0.9
```

超过阈值，任务会被**直接拒绝**（日志里是 `OverLoad`），UI 上可能只显示"提交成功/等待"，看起来像卡住。

虚拟机内存小的时候，默认 0.7 很容易一直拦；但也不要无脑调到 1.0——给系统和 JVM 留余量。

排查：

```bash
grep -i "OverLoad" /opt/dolphinscheduler/worker-server/logs/dolphinscheduler-worker.log | tail
```

## 9. 排障路径（按顺序，别跳）

```
1. UI 看实例状态：是"等待"还是"失败"？
2. 看任务实例：哪个节点失败、耗时多少、退出码多少？
3. 看 worker 日志：真正的报错在这里（UI 只有一句话）
4. 按退出码分流：
   1   → 脚本自己的校验失败
   126 → 没执行权限
   127 → 命令/文件找不到（PATH、路径）
   137 → SIGKILL，通常 OOM
   143 → SIGTERM，通常超时被杀
5. 查资源：内存/磁盘/OverLoad
6. 查环境：租户用户是否存在、PATH 是否加载、数据是否在 worker 本地
```

元数据库直查（比 UI 快）：

```sql
SELECT id,name,state,start_time,end_time FROM t_ds_process_instance ORDER BY id DESC LIMIT 5;
SELECT name,state,start_time,end_time FROM t_ds_task_instance WHERE process_instance_id = ?;
```

## 10. 设计规范

| 规范 | 原因 |
|---|---|
| 脚本必须幂等 | 失败重试、补数都会重复执行 |
| 成功 `exit 0`，失败 `exit 非0` | 调度只认退出码 |
| 一个节点只做一件事 | 失败好定位、重试代价小 |
| 复杂逻辑放脚本/SQL，不塞进 DS | DS 只负责编排 |
| 上游成功才跑下游 | 用 DAG 依赖，不要靠 sleep 等 |
| 关键节点配重试 | YARN 资源瞬时不足很常见 |
| 脚本路径用绝对路径 | worker 不加载 `.bashrc` |
| 任务里显式 `source /etc/profile` | 否则 `hive: command not found` |

## 11. 常见坑（都是项目里真实踩过的）

| 现象 | 根因 | 处理 |
|---|---|---|
| 任务秒失败，提示租户不存在 | 租户填了 `default`（占位租户，不是 Linux 用户） | 改成本机真实用户 |
| `hive: command not found` | worker 的 PATH 没加载 | 在 `dolphinscheduler_env.sh` 里 export，或脚本内 source |
| 从节点跑 DWD 报元数据连接失败 | 各节点 `hive-site.xml` 的账号密码不一致 | 三台统一 |
| 找不到本地切分文件 | 脚本只在 hadoop1 上有数据 | 分发到所有 worker，或固定 worker 分组 |
| 任务一直"等待" | OverLoad / worker 没注册 / 队列堵 | 查日志、查 ZK 注册、查负载 |
| 脚本报 `$'\r': command not found` | 脚本是 CRLF | `sed -i 's/\r$//'`，仓库加 `.gitattributes` |
| 补数跑出来是未来日期 | 把 `$[yyyy-MM-dd-1]` 改成了当天 | 保持 T+1 语义，补数填 D+1 |

## 12. 和 Airflow / Azkaban 的对比（了解即可）

| | DolphinScheduler | Airflow | Azkaban |
|---|---|---|---|
| 语言 | Java | Python | Java |
| 部署 | 多服务 + ZK + DB | 单机/集群 + DB | 单机/集群 |
| 可视化 | 强 | 中 | 中 |
| 补数 | 内置 | 需配置 | 弱 |
| 生态 | Hadoop 友好 | Python 生态强 | 较老 |

选型没有绝对优劣，**能稳定跑、能排障、团队会用**最重要。
