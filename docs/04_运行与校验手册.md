# 运行与校验手册

## 一、环境要求

| 组件 | 版本 |
|---|---|
| Hadoop | **3.1.3**（HDFS + YARN） |
| Hive | 3.1.2（Metastore 在 MySQL 5.7.28） |
| DolphinScheduler | 3.2.2（ZooKeeper 3.8.4） |
| JDK | 8 |
| 集群 | 3 节点（hadoop1 = NameNode + ResourceManager + Metastore + DS master/api/alert；hadoop2/3 = DataNode + NodeManager + DS worker） |

**集群启动**（推荐，一条命令拉起 ZK / HDFS / YARN / DolphinScheduler 并自检）：
```bash
bash /home/cy/scripts/ops/dw-cluster.sh start
bash /home/cy/scripts/ops/dw-cluster.sh check     # 7 项健康检查
```

手工启动（不含 DolphinScheduler，DS 用 `dolphinscheduler-daemon.sh` 单独起）：
```bash
start-dfs.sh
start-yarn.sh
jps        # hadoop1 应看到 NameNode / DataNode / ResourceManager / NodeManager
```

## 三、执行顺序

```bash
# 1. 拆分源数据（按天拆 31 个文件，去表头去 \r，产出 _manifest.txt）
bash scripts/ods/split_source.sh

# 2. ODS
hive -f scripts/ods/ods_ddl.sql
bash scripts/ods/ods_load.sh

# 3. DWD
hive -f scripts/dwd/dwd_ddl.sql
bash scripts/dwd/dwd_load.sh all          # 单天：bash scripts/dwd/dwd_load.sh 2019-10-01

# 4. DWS
hive -f scripts/dws/dws_ddl.sql
bash scripts/dws/dws_load.sh all          # 首次会自动重建首活日维表

# 5. ADS
hive -f scripts/ads/ads_ddl.sql
bash scripts/ads/ads_load.sh all          # 单天：bash scripts/ads/ads_load.sh 2019-10-01
```

**每个 `*_load.sh` 都支持三种用法**：

| 用法 | 说明 |
|---|---|
| `<脚本> 2019-10-01` | 单天增量（日常 T+1） |
| `<脚本> all` | 全量补数（首次建仓 / 重跑历史，走批量 SQL） |
| `<脚本> check` | 只做校验，不写数（仅 ADS 支持） |

> 日常 T+1 由 DolphinScheduler 的 `ods_load → dwd_etl → dws_sum → ads_stat` 工作流调度，
> 部署与补数换算见 [`05_DolphinScheduler部署手册.md`](05_DolphinScheduler部署手册.md)；本文的手工命令用于首次建仓与历史回填。

## 四、耗时参考（3 节点虚拟机）

| 步骤 | 耗时 |
|---|---|
| 拆分源数据 | 约 2 分钟 |
| ODS 上传 31 个分区 | 约 5 分钟 |
| DWD 全量 | 约 10 分钟 |
| DWS 批量补数 | 5~8 分钟（按天循环则需 73 分钟） |
| ADS 批量补数 | 438 秒（按天循环则需 143 分钟） |
| 留存表 + RFM 表 | 各 3~6 分钟 |

> **注意**：上表 ADS 的 438 秒只统计 5 张按天分区表；留存与 RFM 是全期计算，
> **单天模式下每天也会重跑一遍**。因此单天全链路实测约 30 分钟（ods 52s + dwd 132s + dws 368s + ads 1330s），
> 31 天用调度补数按天跑要十几个小时——历史回填请用 `all` 模式。

## 五、校验规则

每层脚本跑完会自动校验，全部通过才打印 `[PASS]`，任一不通过则**退出码非 0**（可被调度系统捕获）。

### ODS

- 各分区行数与 `_manifest.txt` 逐日比对
- 重复上传行数不变（幂等）

### DWD

1. ODS 行数 = DWD 行数（9,244,421）
2. 主键组合唯一
3. 输出文件数检查

### DWS

1. 用户表 GMV = 商品表 GMV（逐日）
2. 用户表与商品表的订单数逐日相等
3. 漏斗表每天恰好 1 行
4. 用户表行数 = DWD 当天去重 `user_id` 数；商品表行数 = 去重 `product_id` 数

> 漏斗表只有人数和转化率，没有金额字段，所以不参与 GMV 比对；它校验的是"每天恰好 1 行"这个粒度约束。

### ADS

1. 大盘 GMV = DWS GMV = 74,948,758.44（按 ADS 已覆盖日期比）
2. 订单数 = 291,157
3. 行数与分区约束（对应脚本里的规则 3）：
   - 大盘/漏斗**每个 `dt` 分区恰好 1 行**（`GROUP BY dt HAVING COUNT(1) > 1` 应恒为 0），且两者天数一致
   - 单天模式校验目标分区已产出，全量模式才校验覆盖 31 天
     （分区表不能数总行数/总天数，见踩坑记录第 11 条）
   - 商品榜每天 ≤ 50 行、品牌榜 ≤ 30 行
4. 品类 GMV 合计 = 大盘 GMV（证明「未知品类」分组没丢数）
5. 新客下单 + 老客下单 = 当日支付人数
6. 留存 cohort 数 = 31；窗口不足的必须为 NULL
7. RFM 用户数 = 维表用户数 = 3,021,953

## 六、关键配置项

所有脚本在 SQL 开头统一设置，改动前请确认理解原因：

```sql
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.exec.parallel = false;        -- Hive 3.1 开并行偶发 ConcurrentModificationException
SET hive.auto.convert.join = false;    -- 302 万行维表走 shuffle join，见踩坑记录第 4 条
SET hive.vectorized.execution.enabled = true;
```

## 七、故障处理

| 现象 | 原因与处理 |
|---|---|
| `Map local work exhausted memory` | map join 打爆 Hive 客户端本地 JVM。调 `mapreduce.map.memory.mb` **无效**，因为它不受 YARN 管。改 `hive.auto.convert.join=false` |
| `hive -f` 报解析错误，但 SQL 看着没问题 | 检查有没有 `/* */` 块注释，尤其文件末尾。Hive 3.1 有此缺陷，全改 `--` 行注释 |
| 任务跑一半 SSH 断开 | 任务多半还在跑。长任务用 `nohup ... > log 2>&1 &`，再轮询日志 |
| 脚本报 `bad interpreter` 或参数带 `\r` | 文件是 CRLF 行尾。推送到 Linux 后执行 `sed -i 's/\r$//' *.sh *.sql` |
| 日志里出现 `$'\204xxx': 未找到命令` | **任务运行期间覆盖了脚本文件**，bash 按旧字节偏移续读到半个汉字。等任务结束再改脚本 |
| DataNode / NodeManager 没起来 | 检查虚拟机网卡（挂起恢复后可能链路 down）；重启后 `start-dfs.sh` / `start-yarn.sh`，从节点会自动重新注册 |

## 八、重跑与回滚

所有 `INSERT` 都是 `OVERWRITE`，**天然幂等**：同一天重复执行结果不变，可以直接重跑。

- 重跑某一天：`<脚本> 2019-10-01`
- 重跑整个月：`<脚本> all`（动态分区只覆盖本次产出的分区，不会误删其他月份）
- 需要回到干净状态：先 `hive -f <层>_ddl.sql` 重建表（DDL 里带 `DROP TABLE IF EXISTS`），再跑 `all`
