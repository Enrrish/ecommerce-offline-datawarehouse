# 分层设计与建模

## 一、为什么分层

不分层的话，所有指标都从明细表直接查，会带来三个问题：

1. **重复计算** —— 同一个 `SUM(price)` 被十个人写了十遍，每人写的还不一样；
2. **口径漂移** —— 今天改了过滤条件，历史报表跟着变，没人知道哪个数是对的；
3. **排查困难** —— 指标错了不知道错在哪一步。

分层的核心目的是**把"清洗"、"聚合"、"口径"这三件事拆到不同的层里各做一次**，
出问题能定位到具体某一层，改口径只改一层。

## 二、各层职责边界

| 层 | 回答的问题 | 允许做什么 | 不允许做什么 |
|---|---|---|---|
| **ODS** | 原始数据长什么样 | 只做格式转换和分区 | 不做过滤、不改字段值、不做业务判断 |
| **DWD** | 一条干净的行为记录是什么 | 类型转换、去空、去重、加派生字段 | **不做业务过滤**（保证行守恒）、不做聚合 |
| **DWS** | 某个主题域的汇总是多少 | 按主题粒度聚合，**引入业务口径** | 不做跨主题 join、不做 TOP N 截断 |
| **ADS** | 某个具体报表要什么数 | 跨主题 join、窗口排名、分层打标、按需截断 | 不承载明细查询 |

> **最容易被问到的两个边界**
> - **DWS 和 ADS 的区别？** DWS 粒度由**数据模型**决定（用户×天、商品×天），ADS 粒度由**看板需求**决定（可能只取 TOP 50、可能跨主题）。所以 ADS 允许冗余——只要看板好用。
> - **为什么 DWD 不做过滤？** 一旦过滤，ODS 与 DWD 行数就对不上，清洗掉了什么、为什么掉，事后无从审计。本项目把"行守恒"当作一条硬约束：DWD 行数必须严格等于 ODS（9,244,421）。

## 三、ODS 层设计

```
ods_user_behavior_di   （_di = day increment，日增量）
```

| 设计点 | 选择 | 理由 |
|---|---|---|
| 表类型 | **外部表** | 误执行 `DROP TABLE` 不会删掉 HDFS 上的原始数据 |
| 字段类型 | **全 STRING** | 源数据有空串和脏值，在 ODS 定成数值类型会让异常值不可逆地变成 NULL，排查时无法还原原始值 |
| 文件格式 | TEXTFILE + OpenCSVSerde | 贴源层保持可读可比对 |
| 分区 | `dt`（日） | 下游按天调度、按天回溯 |
| 建库 | `CREATE DATABASE` 不指定 LOCATION | 避免托管表落进贴源区目录，造成 ODS 与数仓目录混在一起 |

**上传幂等**：`ods_load.sh` 每次先 `rm -r -f` 分区目录再 `put`，然后 `ADD IF NOT EXISTS PARTITION`，最后拿 `_manifest.txt` 回验行数。重复执行行数不变。

## 四、DWD 层设计

```
dwd_user_behavior_di   （内部表，ORC + Snappy）
```

| 设计点 | 选择 | 理由 |
|---|---|---|
| 表类型 | 内部（托管）表 | 数据由 ODS 派生，可重建，不需要外部表保护 |
| 格式 | ORC + Snappy | 459.8 MB vs CSV 1.1 GB，省 58%；ORC 支持列裁剪，下游只取几列时 I/O 大幅下降 |
| 分区 | `dt` | 与 ODS 对齐，便于逐日核对 |
| 去重主键 | `event_time + user_id + product_id + event_type + user_session` | 五元组能唯一标识一次行为 |
| tie-breaker | 有 `brand` / `price` 的记录优先 | 避免 `ROW_NUMBER` 随机丢弃掉信息更全的那条 |

**六道工序**：取数（`WHERE dt = bizdate`）→ 类型收敛 → 空串转 NULL → 主键去重 → 加 `event_hour` → 写出。**全程无 WHERE 过滤。**

## 五、DWS 层设计

按**主题域**划分，本项目三个主题：用户、商品、漏斗，外加一张维表。

```
dim_user_first_active      用户首活日（维表雏形，非分区）
dws_user_action_day        用户 × 天
dws_product_action_day     商品 × 天
dws_user_funnel_day        天（每天 1 行）
```

### 为什么首活日要固化成维表

现算 `MIN(dt)` 有两个致命问题：

1. **性能** —— 每次都要全表扫描 31 天；
2. **正确性** —— 倒序补数时会算错：先跑 10-05 再跑 10-01，跑 10-05 时该用户首活日被记成 10-05，等跑到 10-01 才发现他其实 10-01 就来过，但 10-05 的数据已经写完了。

固化成一张 302 万行的小表，join 一次即可，又快又准。

### 商品维度为什么取"日快照"

`category_code` / `brand` 取**当天事件里的值**（`MAX()` 忽略 NULL），不做全期回填。

原因是全期最新值会让历史报表**回溯变形**：今天某个商品改了品牌，昨天甚至上月的报表也跟着变。
日快照保留了变更痕迹，虽然单看某天可能缺失，但历史是可信的。

## 六、ADS 层设计

原则：**一表一需求**，每张表对应看板上的一个页面，字段名直接对齐展示，业务方不用再写 SQL。

```
ads_trade_overview_day     大盘：规模与产出（看板第一屏）
ads_user_funnel_day        用户：转化与人群结构
ads_user_retention_day     用户：新增留存（Cohort）
ads_user_value_rfm         用户：价值分层（全期快照）
ads_product_rank_day       商品：热销榜 TOP 50
ads_category_sales_day     商品：品类分析（含一级品类下钻）
ads_brand_sales_day        商品：品牌榜 TOP 30
```

**两种调度模式**（这是本项目 ADS 层的一个实际设计点）：

| 模式 | 适用 | 说明 |
|---|---|---|
| 按天增量 | 日常 T+1 | `WHERE dt = 常量` + 静态分区，只算一天 |
| 全量重算 | 留存表、RFM 表 | 这两张表天然是全期计算——10-05 新增的用户要等到 10-12 才知道他 7 日是否留存，无法按天增量。**两种调度模式下都必须重跑** |

## 七、命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 数据库 | 业务库名 | `mydb` |
| ODS/DWD 表 | `<层前缀>_<主题>_<增量方式>` | `ods_user_behavior_di`、`dwd_user_behavior_di` |
| DWS 表 | `dws_<主题>_<粒度>` | `dws_user_action_day` |
| ADS 表 | `ads_<主题>_<用途>_<粒度>` | `ads_trade_overview_day` |
| 维表 | `dim_<实体>_<属性>` | `dim_user_first_active` |
| 分区字段 | `dt`（`yyyy-MM-dd`） | |
| 计数 / 金额 / 比率 | `_cnt` / `_gmv` / `_rate` | `view_cnt`、`total_gmv`、`view_to_pay_rate` |

`_di` = day increment（日增量），`_day` = 日粒度汇总。

## 八、存储与性能

| 层 | 格式 | 压缩 | 实测体积 |
|---|---|---|---|
| 源数据 | CSV | — | 1.2 GB |
| ODS | TEXTFILE | — | 1.207 GB（全表扫描触发 5 个 Map） |
| DWD | ORC | Snappy | 459.8 MB |
| DWS / ADS | ORC | Snappy | MB 级 |

**分区裁剪效果**：查询单天分区读 34.9 MB / 1 个 Map；不分区裁剪全表读 1.207 GB / 5 个 Map。
这就是为什么分区字段必须是所有查询的第一过滤条件。
