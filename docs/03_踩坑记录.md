# 踩坑记录

按实际发生顺序整理。这些是真实遇到过、排查过、解决过的问题，
不是从教程上抄来的注意事项——每一项都写清了**现象 → 排查 → 根因 → 解法 → 教训**。

---

## 1. HDFS 的真实数据目录不在 `/user` 下

**现象**：清空数仓时删掉了 `/user/hive/warehouse` 和 `/origin_data`，但磁盘占用没降下来，怀疑数据没删干净。

**排查**：查了 `core-site.xml`，发现配置了 `hadoop.tmp.dir=/home/cy/hadoopdata`，而 `hdfs-site.xml` 里**没有显式配置** `dfs.namenode.name.dir` 和 `dfs.datanode.data.dir`。

**根因**：只配了 `hadoop.tmp.dir` 时，NameNode 和 DataNode 会默认落在 `${hadoop.tmp.dir}/dfs/name` 和 `${hadoop.tmp.dir}/dfs/data`，也就是 `~/hadoopdata/dfs/`，而不是常见的 `/data/hadoop` 或 `/opt/hadoop/data`。所以真正的块数据在 `~/hadoopdata` 里。

**教训**：清理 HDFS 数据前先看 `core-site.xml` + `hdfs-site.xml` 确认真实数据目录，凭经验猜路径会误删或漏删。

## 2. Hive 3.1 里 `hive -f` 执行文件末尾的 `/* */` 块注释会解析失败

**现象**：SQL 文件在末尾写了一段块注释 `/* ... */` 作为说明，`hive -f` 直接报语义/解析错误，但同样的内容改成行注释没问题。

**根因**：Hive 3.1 对文件末尾块注释的解析有缺陷。

**解法**：全项目的 SQL 注释统一改成 `--` 行注释。

**教训**：Hive SQL 脚本一律用 `--`，不要图省事用 `/* */`，尤其不要放在文件末尾。

---

## 3. `hive.exec.parallel=true` 抛 `ConcurrentModificationException`

**现象**：开了并行执行后，某些多 INSERT 脚本随机报 `ConcurrentModificationException`。

**解法**：`SET hive.exec.parallel=false;`。集群只有 3 个节点、资源本就紧张，并行的收益有限，稳定性优先。

---

## 4. map join 302 万行维表 OOM，且调 `mapreduce.map.memory.mb` 完全无效 ★

**现象**：DWS 层 join 首活日维表（3,021,953 行）时报 `Map local work exhausted memory`。

**排查**：第一反应是加大 map 内存，于是调 `mapreduce.map.memory.mb`、`hive.mapjoin.localtask.max.memory.usage`，**全都没用**。

**根因**：这是最容易踩的认知误区——**map join 的"本地任务"（MapredLocalTask）运行在 Hive CLI 自己的 JVM 里，不在 YARN 容器里**。所以调 YARN 侧的 `mapreduce.map.memory.mb` 根本影响不到它，它受限于 Hive 客户端启动时的 `-Xmx`（本项目只有 `-Xmx256m`）。

**解法**：`SET hive.auto.convert.join=false;`，强制走普通 shuffle join。302 万行的维表走 shuffle 完全可接受。

**教训**：Hive 里有两套内存体系——YARN 容器内存和 Hive 客户端本地 JVM 内存。报 `Map local work exhausted memory` 时要改的是后者（或干脆禁用 map join），不要去调 `mapreduce.*`。

## 5. 按天循环跑 DWS 需要 73 分钟，改成批量后 7 分钟 ★

**现象**：`dws_load.sh 2019-10-01` 单天耗时 142 秒，31 天循环下来要 **73 分钟**；ADS 层同样问题，单天 277 秒 × 31 天 = **143 分钟**。

**根因**：循环每次都要重新 shuffle 一遍 302 万行的维表、重新启停一次 MR，固定开销被重复支付 31 次。

**解法**：另写一份批量 SQL（`dws_backfill.sql` / `ads_backfill.sql`），改成**一次 `GROUP BY dt` + 动态分区写入**，维表只 join 一次。DWS 从 73 分钟降到 5~8 分钟，ADS 从 143 分钟降到 **438 秒**（快约 19 倍）。

**关键**：两套 SQL 的指标口径必须完全一致——只是把 `WHERE dt = 常量` 换成 `GROUP BY dt`、把 `ROW_NUMBER() OVER ()` 换成 `OVER (PARTITION BY dt ...)`，并且用同一套校验脚本验证结果相同。

**教训**：数仓里"日常增量"和"历史补数"是两种优化目标，前者优化单次执行成本，后者优化总量成本，**必须写两套 SQL**。这也是为什么本项目 `scripts/` 下每个中间层都有 `*_etl_day.sql` 和 `*_backfill.sql` 两个文件。

## 6. SSH 前台执行长任务，每 141 秒才吐一行输出，结果 300 秒超时断开

**现象**：通过 SSH 前台跑一个 10 分钟的 Hive 任务，连接在第 300 秒超时断开。**但任务其实还在集群上跑**。

**根因**：Hive CLI 的日志输出有缓冲，不是实时的，SSH 连接长时间没有数据交互就被判定超时。

**解法**：长任务一律用 `nohup ... > log 2>&1 &` 放后台，再轮询日志文件看进度。

**教训**：别用前台 SSH 跑长任务，超时断开会让你误以为任务挂了，实际上它可能正在写数据——重复提交反而会造成数据混乱。

## 7. 任务运行期间覆盖脚本文件，导致 bash 读到乱码命令 ★

**现象**：脚本正在后台运行时，我用 sftp 覆盖了同一个 `.sh` 文件，随后日志里出现：
```
ads_load.sh:行165: $'\204表规模': 未找到命令
```
但检查文件字节完全正常（`echo "[INFO] ADS 各表规模"` 的 UTF-8 编码无误）。

**根因**：bash 是按**字节偏移**逐块读取脚本文件的。文件被就地覆盖后长度变化，运行中的 bash 仍从旧偏移继续读，读到的字节边界正好落在一个中文字符的中间（"各" = `E5 90 84`，从 `84` 开始读），于是把半个汉字当成了命令名。

**教训**：**任务运行期间绝对不要覆盖它正在执行的脚本**。要改就等它结束，或者写到新路径。

## 8. 校验基准写错：拿 ADS 一天的数据去比 DWS 全月

**现象**：单天模式下跑完，校验报 `GMV 不一致 dws=74948758.44 ads=1840032.18`。

**排查**：ADS 只写了 10-01 一天，而校验脚本里 DWS 侧统计的是全月 31 天——**比较对象错了，不是数据错了**。

**解法**：改成按"ADS 已覆盖的日期"来比：
```sql
SELECT ROUND(SUM(d.total_gmv),2), SUM(d.purchase_cnt)
FROM dws_user_action_day d
JOIN (SELECT DISTINCT dt FROM ads_trade_overview_day) a ON d.dt = a.dt;
```
这样单天模式只比当天、全量模式比全月，一套校验适配两种模式。

**教训**：写校验脚本时先想清楚"比较的边界是什么"，否则会为了一个假故障浪费时间，更糟的是让人误以为数据有问题而反复重跑。

## 9. RFM 里 NTILE 的两个陷阱 ★

**陷阱一：对离散值用 NTILE，并列值会被随机切进不同桶。**
购买次数是离散小整数，绝大多数用户只有 1 次。`NTILE(5) OVER (ORDER BY frequency)` 会把大量 `frequency=1` 的用户按 row_number 顺序切到不同桶——**同样的行为拿到不同的分数**。
→ 改用固定区间打分（1 次=1 分，2 次=2 分，3 次=3 分，4-5 次=4 分，≥6 次=5 分）。

**陷阱二：NTILE 的分桶集合如果包含不该参与的对象，结果全废。**
本来想一次扫描给所有用户打分，但 302 万用户里 281 万从未购买（`monetary=0`），他们会**把第 1 桶占满**，导致真正有购买的 20 万用户全被挤到第 5 桶，M 分完全失真。
→ 必须对购买用户子集单独分桶（`WHERE frequency > 0`），未购买用户不参与打分、单独归入"未购买用户"层。

**顺带的设计选择**：R 也用固定区间而非 NTILE，因为"最近 7 天内购买过"本身就是明确业务信号，固定阈值才能让**不同月份的分层结果横向可比**；等频分桶会让分数随当月数据分布漂移。

## 10. 数据集首日的新用户全是"伪新客" ★

**现象**：留存表里 2019-10-01 这个 cohort 有 188,895 个"新用户"，次日留存 8.44%，明显高于其他日期的 4~6%。

**根因**：数据从 2019-10-01 才开始，这天出现的所有用户都会被判成首次活跃——**他们其实是存量用户**。存量用户的粘性天然高于真新客，所以留存率虚高。

**解法**：留存表加 `is_data_start_cohort` 字段标记数据集首日的 cohort，看数时排除；同时在表注释和 README 里写明。

**教训**：用"首活日"定义新用户时，**数据集的时间边界会造成系统性偏差**，第一天（甚至前几天）的新客数都不可信。这是分析类指标最常见的坑之一。

## 11. 分区表校验不能数总行数：规则 3 把「每天 1 行」写成了「总共 1 天」 ★

**现象**：补数任务跑到最后一步 `ads_stat`，耗时 22 分钟后失败。前序 ods/dwd/dws 全部成功（52s / 132s / 368s）。第一反应是超时或 OOM——都不是。

**排查**：先看 `t_ds_task_instance` 的耗时列，再看 worker 日志末尾的退出码，**退出码决定了排查方向**：

| 退出码 | 含义 | 该往哪查 |
|---|---|---|
| 1 | 脚本自己判断失败后 `exit 1` | 脚本内的校验逻辑 |
| 126 | 无执行权限 | chmod |
| 127 | 命令/文件不存在 | 路径、环境变量 |
| 137 (128+9) | 被 SIGKILL | OOM killer（`dmesg \| grep -i oom`） |
| 143 (128+15) | 被 SIGTERM | 调度超时 kill |

本次是 `exitStatusCode:1`，日志末尾写着 `[FAIL] ADS 层有 1 项不通过`——脚本跑完了，是自己的校验没过。
另外 DS 侧 `taskTimeout=2147483647` 是默认值，等于没有超时保护，**不是它杀的**。

**根因**：校验里写了一句"单天模式只应有 1 天数据"（`EXPECT=1`），但 ADS 是**按天分区表**，历史分区本来就要保留——单天增量后 `COUNT(DISTINCT dt)` 必然是 31 而不是 1。

```
[OK]   规则3 大盘/漏斗天数一致 = 31
[FAIL] 规则3 覆盖天数=31 期望=1
```

规则 3 的真实语义是"**每个 dt 分区内恰好 1 行**"，被错误实现成了"表里总共只有一天"。

**解法**：把两个维度拆开，各用各的口径：

```sql
-- 真正的语义：不应存在行数 >1 的日期
SELECT COUNT(1) FROM (SELECT dt FROM ads_trade_overview_day GROUP BY dt HAVING COUNT(1) > 1) dup;  -- 应恒为 0
-- 单天模式：只校验本次目标分区已产出
SELECT COUNT(1) FROM ads_trade_overview_day WHERE dt = '$MODE';  -- 应 = 1
```

"覆盖天数"只在全量模式下校验（应等于 DWS 天数），单天模式改为校验目标分区。

**教训**：增量 pipeline 里**不能用表级总量/总天数做校验**，分区表的历史数据会累积。这和条目 8 是同一类错误——校验边界没想清楚：8 是比错了对象，这条是数错了维度。

## 12. 自检脚本数错 DataNode：`grep -A5` + `grep -c` 的静默陷阱 ★

**现象**：`dw-cluster.sh check` 报 `Live datanodes = 2/3`，看着像有一个 DataNode 没起来。

**排查**：三台 `jps` 都有 DataNode，`hdfs dfsadmin -report` 里三个节点 Last contact 都是刚才、Decommission Status 全是 Normal——**HDFS 完全健康，是脚本报错**。

**根因**：

```bash
live=$(hdfs dfsadmin -report | grep -A5 "Live datanodes" | grep -cE "hadoop[0-9]")
```

两个默认值叠在一起出错：`-A5` 只覆盖到**第一个** DataNode 的前 5 行，而其中 Name 行和 Hostname 行都含主机名；`grep -c` 数的是**行数不是匹配次数**——一行里出现两次也只算 1。结果恒等于 2。

**解法**：Hadoop 已经把这个数算好了，直接拿：

```bash
live=$(hdfs dfsadmin -report | grep -m1 "^Live datanodes" | grep -oE '\([0-9]+\)' | tr -d '()')
```

**教训**：能直接取现成统计值就别自己抓文本拼。`grep -A n` 的窗口大小、`grep -c` 数行不数次，都不会报错，只会悄悄给你一个差 1 的结果。**自检脚本出假阳性比不做自检更糟**——它让人去"修"一个根本不存在的问题，这次差点为此重启整个集群。

## 13. 其他小坑

| 现象 | 解法 |
|---|---|
| SSH 连不上虚拟机 | 网段搞错了，实际是 `192.168.10.x` 不是 `192.168.101.x` |
| hadoop1 挂起恢复后集群不可用 | 虚拟网卡链路 down，需要重启该虚拟机，再 `start-dfs.sh` / `start-yarn.sh`；从节点的 DataNode/NodeManager 会自动重新注册 |
| Python 升级后 paramiko 丢失 | `pip install paramiko` 重装 |
| 本地脚本推送到 Linux 后有 `\r` | 推送后统一 `sed -i 's/\r$//'`，否则 bash 报 `bad interpreter` 或参数带 `\r` |
| 自动化工具的默认命令超时是 120 秒 | 需要长等待时显式传超时参数，否则命令会被 SIGTERM 掉 |
