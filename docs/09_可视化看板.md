# 可视化看板

> 把 ADS 层的 7 张结果表变成一页能看懂的经营看板。不上 BI 工具、不引新组件，
> 用「Hive 导出静态 JSON + ECharts 单页」的方式实现，产物是一个可以双击打开的 HTML。

## 一、选型：为什么不用 Superset / Metabase / DataEase

先看这台机器的真实条件（2026-10-28 实测）：

| 项 | 实测值 | 对选型的影响 |
|---|---|---|
| ADS 数据量 | 7 张表合计 **14.6 MB**（RFM 13.8 MB / 302 万行，其余 6 张 < 1 MB） | 数据极小，任何工具都不会受限于"量" |
| 运行时 | 只有 **Python 2.7**；无 python3、无 pip、**无 node**；Java 8 | Superset 要走 py3 + 编译依赖，最重的一条路 |
| HiveServer2 | **未启动**（10000 不通） | 看板不能直连 Hive：每次 `hive -e` 冷启动 ≈6 s，10 个图要 60 s |
| MySQL | 5.7.28，在 hadoop1:3306 | 可做应用层数据集市，但没有现成同步工具（无 Sqoop） |
| 内存余量 | hadoop1 仅剩 **1.5 GB**（swap 已用 1.9 GB）；hadoop2 3.4 GB；hadoop3 3.7 GB | JVM 系 BI 只能装 hadoop2/3，装 hadoop1 会挤垮 MySQL/DS |

由此排除：

| 方案 | 需要新增 | 内存 | 结论 |
|---|---|---|---|
| **静态 ECharts + JSON** | 无 | ~0 | ✅ 采用 |
| Metabase | JDK 11 + JAR | 1~1.5 GB | 现环境 Java 8，换 JDK 有连带风险 |
| Superset | python3 + pip + 编译依赖 | 1.5~2 GB | 装 py3 的坑最多 |
| DataEase | Docker / 安装包 | 1.5~2 GB | 无 Docker，且挤内存 |
| Spring Boot 自研 | JDK8 + Maven | 300 MB | 可行，但工作量是静态版 3 倍 |

关键判断：**离线数仓本来就是 T+1，一天只产一次数**。看板读静态文件不是"简化版"，而是与业务节奏匹配的正确形态；真正的实时需求该项目并不存在。

## 二、整体链路

```
Hive mydb.ads_*（7 张表）
        │  scripts/ads/ads_export.sh
        ▼
dashboard/data/*.json + *.js   （7 个数据集 + meta，合计 2.6 MB）
        │
        ▼
dashboard/index.html + echarts.min.js   （纯前端，无后端、无 CDN 依赖）
```

- 导出用 `hive -S -f` 直接产出 JSON 数组，**不做二次转换**；
- 同时写 `.json`（给其他系统用）和 `.js`（`window.DATA_XXX = [...]`）；
- 页面用 `<script src>` 加载 `.js` 而不是 `fetch`，因为浏览器在 `file://` 下会拦 fetch 本地文件，而 `.js` 不受限——这样双击 HTML 就能看，不必起服务。

## 四、怎么跑

**1) 生成数据**（在任一同 Hive 环境通的节点执行）

```bash
bash scripts/ads/ads_export.sh          # 默认输出到 /home/cy/dashboard/data
OUT=/tmp/d bash scripts/ads/ads_export.sh   # 指定输出目录
```

**2) 看板**

- 本地：直接双击 `dashboard/index.html`（`echarts.min.js` 与 `data/` 必须同级）；
- 集群上：`cd /home/cy/dashboard && python -m SimpleHTTPServer 18080`，浏览器开 `http://192.168.10.129:18080/`（实测 index / echarts / data 均返回 200）。

**3) 挂进调度**

在 DolphinScheduler 的 ADS 任务之后加一个 Shell 节点：

```bash
bash /home/cy/scripts/ads/ads_export.sh
```

⚠️ **脚本必须同步到 hadoop2 / hadoop3**——DS 的 Worker 只在这两台，任务不会在 hadoop1 上执行（这个坑已经踩过一次，见 `docs/03` 第 17 条）。当前三节点 md5 已一致。

## 五、口径提醒（看板上的坑都写在图注里）

1. **2019-10-01 是伪新客**：数据集首日所有存量用户都被判成"新客"，新客占比 100%、次日留存 16.9% 都不可信。KPI 的"新客占比"已剔除首日，图表上另有文字说明。
2. **加购人数 < 支付人数**是正常的：大量用户跳过加购直接下单，所以 `cart_to_pay_rate` 会 > 100%，漏斗只画 活跃→浏览→支付 三级，不画加购。
3. **留存空白格 ≠ 0**：靠后的 cohort 窗口不足，ADS 里是 NULL，热力图留空。
4. **RFM"未购买用户"占 93%**：直接画饼图会把其余 8 类压成一条线，所以图和表都只展示有过购买行为的 8 类人群。

## 六、实现踩坑

| # | 现象 | 原因与解法 |
|---|---|---|
| 1 | `Invalid function to_json` | Hive **4** 才有 `to_json()`，3.1.2 没有。改用 `concat()` 手工拼 JSON |
| 2 | 留存导出只有 **24 行**（表里 31 行） | `concat()` 只要有一个参数是 NULL 就返回 NULL，`collect_list` 会**静默丢掉** NULL 元素——后期 cohort 的 `retain_1d/3d/7d` 是 NULL。给所有可能为空的数值字段套 `COALESCE(..., 'null')` |
| 3 | `regexp_replace(x, '"', '')` 在 `hive -f` 里报 `extraneous input ';'` | 双引号字面量触发 Hive 3.1 的解析问题（同样的写法在另一条 SQL 里却能过）。改用 `replace(x, chr(34), '')`，彻底不写双引号 |
| 4 | 页面双击打开是空白 | `file://` 下 `fetch('data/*.json')` 被 CORS 拦。改为导出 `window.DATA_*` 赋值的 `.js` 文件 |
| 5 | 漏斗标签串到隔壁卡片 | 卡片只有 1/3 屏宽，`名称+人数+百分比` 太长。标签只留两字阶段名，人数与转化率放到图下方一行 |
| 6 | 热力图底部色标压住日期标签 | `grid.bottom` 从 64 加到 104，`visualMap` 挪到 `bottom:4` |
| 7 | 品类饼图图例被卡片裁掉 | 去掉外置引线标签（`label:false`），图例改 `top:'middle'` + `itemGap:7` |

另外，导出时用 `python -c "json.load(...)"` 做**真正的 JSON 解析校验**，而不是靠"首尾字符是不是 `[` `]`"这种土办法——上面第 2 个坑就是靠它才暴露的。

## 七、性能

| 环节 | 耗时 | 说明 |
|---|---|---|
| `ads_export.sh` | **219 s** | 8 次 Hive CLI 冷启动（每次 ≈6 s）+ 3 个聚合 MR（product/category/brand 全期聚合） |
| 页面首次加载 | < 1 s | 本地文件，2.6 MB，其中 ECharts 1 MB（可换 CDN 版省掉） |
| 交互（切日期） | 即时 | 数据全在浏览器内存里，纯前端过滤 |

若要把导出从 219 s 压下去，方向是**合并成一次 `hive -f`**（8 条 SQL 写一个文件），能省 7 次冷启动 ≈ 40 s；聚合本身可以靠一张中间表一次算完再拆三个榜单，但那是 ADS 层的事，不在看板范围内。
